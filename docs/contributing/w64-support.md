# Sony Wave64 container scope

`@edge-ffmpeg/containers` exports `openW64`, `probeW64`, `muxW64`, `validateW64Output`, `supportsW64Codec` and their types from `src/w64.ts`. Failures use `WavError`, because native implements w64 inside `wavdec.c`/`wavenc.c`. The finite audio backend supports explicit `-f w64` input/output, automatic detection when the input starts with the native riff GUID and carries the wave GUID at byte 24 (more than 40 bytes, as `w64_probe` requires), and the `.w64` output extension. The default encoder is pcm_s16le. Other magic numbers keep their existing four-byte probe; only a lowercase `riff` prefix triggers the 40-byte GUID read.

Supported codecs are the WAV path's eight: pcm_u8, pcm_s16le, pcm_s24le, pcm_s32le, pcm_f32le, pcm_f64le, pcm_alaw and pcm_mulaw. The fmt payload is the native-profile WAV `ff_put_wav_header` output (shared `wavLayout`/`wavHeader`, default compliance): WAVEFORMATEXTENSIBLE for non-canonical masks, rates above 48000 Hz and integer PCM wider than 16 bits, with masks of 0x40000 and above serialized as 0. Other codecs, including big-endian PCM, are refused before output creation, as native refuses them in `w64_write_header`.

## Demux

Input requires a finite range handle. The 40-byte riff/wave header and every 24-byte GUID chunk header are read in bounded pieces. Each fmt chunk contributes at most 40 payload bytes and each fact chunk 8. Data and unknown chunks are skipped by offset without payload reads. As natively, the walk continues to EOF and ignores the declared riff size, apart from the native lower bound of 72. Fewer than 24 trailing bytes end the walk. A chunk size of 24 or less, or one that overflows, ends the walk after data and is invalid before it. Non-data chunks advance by the 8-byte-aligned size. Data advances by its unaligned size, as `avio_skip(size - 24)` does. Packets come from `openRawPcm` over the data range, so seeks, packet budgets and timestamps match the WAV path. The CLI reuses WAV's PCM packet span, seek-at-EOF refusal and channel-layout rules.

Native's data size includes the zero padding its muxer adds to reach an 8-byte boundary, and the native demuxer returns that padding as audio. `durationSamples` therefore counts the padding samples. For example, 3 s16 mono samples demux as 4 and copy to 4. `factSamples` keeps the declared positive fact count separately. When the padded data is not a whole number of frames (for example s24 mono, or 8-bit with three channels, at most lengths), native emits a short final packet and drops or rejects its remainder when decoding. That path is not modelled, and `openW64` refuses it explicitly ("partial sample frame").

The following are also refused explicitly: summary-list metadata chunks, multiple fmt or data chunks, data before fmt, data extending past EOF (native reads to EOF), fact chunks shorter than 32 bytes, packed valid-bit extensible formats, non-PCM subtype GUIDs and a sample frame larger than the read budget. A leading ID3v2 tag, which native skips, fails detection or the riff GUID check. Native-written zero-sample files (data size 24) fail to open, matching native.

## Mux

Output requires a known sample count and is written sequentially, without seeks. The header carries the final values native's seekable trailer writes: file size at 16, an fmt chunk of `align8(24 + fmt)` bytes, a 32-byte fact chunk for non-PCM tags (float, A-law, mu-law), and a data size of `24 + align8(data)`, followed by data and up to 7 zero pad bytes. The fact count is the sample count. Native computes `maxpts - minpts + last_duration` with `minpts` starting at 0 (w64 has no init), so an empty output writes 0, not the WAV path's 1. Every tested seek, trim and frame-limit profile emits pts from 0. w64 writes no metadata, so `-bitexact`, `-fflags +bitexact` and plain output give identical bytes. Packet validation (sample alignment, contiguous zero-based timestamps, exact byte count) is shared with WAV. The destination commits only after every byte succeeds, and any failure aborts it once. `validateW64Output` performs the same header validation (codec, geometry, mask, 64-bit size limit) without allocating, and the CLI calls it before opening the output.

## Evidence

On the pinned macOS arm64 oracle (`.build/reference`, ffmpeg sha256 `1b86106f…`):

- `tests/differential/w64.test.ts`: 192 complete-file mux comparisons (eight codecs, 1/2/3 channels, 8000/96000 Hz, 1/3/8/67 samples, `-bitexact -f w64`). For the 146 native-written files whose padded data is whole frames, the tests check info, packet bytes against native `-c:a copy -f <raw>`, CLI copy framecrc, `-cpuflags 0` s16le decode and CLI w64-to-w64 copy, all byte-exact. The 46 partial-frame files are checked for the explicit refusal. A further 192 timing cases cover eight codecs, four profiles (none, input and output seek with duration, `-frames:a 2`, input seek with duration), copy and a fixed-volume/asetnsamples/asetrate chain, each written as framecrc, w64 and WAV. Further cases cover seek-at/beyond-EOF refusals, `.w64` extension, `-f w64` declarations, w64 to WAV with metadata, empty and `-frames:a 0` outputs, and refusals that native also rejects.
- `tests/unit/w64.test.ts`: crafted-chunk bounds and read-offset checks, seeks, detection, fmt mapping, malformed and limit refusals, padding and empty-fact layout, chunked writes, abort-once and cancellation.
- `tests/workers/w64.test.ts`: 48 workerd cases (eight codecs, 8000/96000 Hz; mux, auto-detected copy framecrc, w64 to WAV), each with at most 64-byte reads and writes and committed output, plus an uncommitted refusal.

Native comparisons were run on macOS arm64 only. Canonical Linux reproducibility, production Workers, R2-backed w64 I/O, checkpointed (unknown-length) w64 mux, the FLAC decode-to-w64 path, the audio checkpoint pipeline, and pipe or non-seekable output (where native leaves placeholder sizes and omits fact) remain unimplemented or unverified.
