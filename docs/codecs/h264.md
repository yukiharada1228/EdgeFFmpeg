# H.264 decoder API integration

`@edge-ffmpeg/avcodec` exposes `createH264Decoder`, `createAvcDecoder`,
`parseAvcConfiguration`, `avcPacketToAnnexB`, `H264InputError`, and `H264ResourceError`.
The caller supplies a trusted, compatible, precompiled `WebAssembly.Module`.
The package does not download codecs or execute Native FFmpeg.

The Annex B decoder consumes complete access-unit packets and returns owned
I420 frames. The AVC adapter accepts configuration records and length-prefixed
access units. Call `flush()` until it returns `null`, then `close()`; cancellation
and errors also close retained decoder references. Packet clocks use `bigint`.

All resource limits are explicit: packet/frame bytes, Wasm memory, combined
payload reservation, pending packets, NAL count, and retained display bytes.
`initialReorderDelay` is an explicit packet-decoder parameter. The MP4 CLI
backend derives its initial delay from indexed PTS using the pinned Native MOV
17entry insertion-depth algorithm. Memory reservations and Wasm linear
memory measurements do not establish total Worker isolate memory usage.

This is an integration in progress. Module-injected MP4-to-rawvideo CLI
decoding is connected. Scoped differential and workerd contracts now cover
72self-owned streams and859frames; the decoder and aggregate codec manifest
entries are `partial`. Final binary/source release assembly and a current-tree
full compatibility report remain pending. Unsupported
bit depths/chroma layouts, interlaced/SVC behavior, damaged-stream concealment,
general MMCO/recovery handling and sequence-reinitialization equivalence remain
incomplete or unverified. Arbitrary byte-stream fragmentation is not supported
by this packet API.

The display policy clears its POC history at an explicit reset boundary, so
MMCO5 does not incorrectly increase the inferred reorder delay. Unit tests
cover this history reset and draining pictures across a non-key boundary.
The pinned module now uses ABI2: an explicit version export and18metadata
words, including the MMCO5 reset flag. The decoder rejects older metadata
ABIs before creating a decoder. Progressive POC types1/2 and the MMCO5
metadata path are integrated; their scoped evidence includes frame-number
wraps, signed deltas, repeated resets, multiple slices and B-picture direct
prediction. This does not establish general H264 conformance.

The presentation and parameter-set adaptations retain LGPL-2.1-or-later notices
and source in `packages/avcodec/src/h264`. A separately supplied codec binary
has its own source, build, licensing and distribution requirements.

The reproducible codec build entry point is `npm run codec:h264:build --
--source /path/to/clean/openh264 --emsdk /path/to/emsdk --out <new-directory>`.
The pinned source, toolchain and artifact hashes are in
`tools/codecs/openh264/build.lock.json`; see that directory's README.
The output includes a separate source checkout, Wasm, link map and compiler/
archive receipt. The build directory is not a release distribution package.

`stage-source.mjs` prepares a sample-media-free corresponding-source snapshot.
Its standalone rebuild verifies a pinned372file manifest and builds in a
separate output directory without Git metadata in the SDK source. This source
staging still needs compiler-runtime notices and final release assembly.

## MP4-to-rawvideo CLI path

A module-injected `createMediaBackend({h264})` uses the existing MP4 stream
selection and transactional output group. `H264BackendConfiguration` supplies
the trusted module and explicit packet/frame/Wasm/display/NAL budgets. The
execution context supplies the total resident, I/O and pending-packet budgets;
index and I/O reservations are subtracted before codec creation.

The Node launcher accepts a pinned codec file explicitly:

```sh
npm run ffmpeg -- --root /path/to/media \
  --h264-wasm .build/codecs/openh264/openh264.wasm -- \
  -f mp4 -i /input.mp4 -map 0:v:0 -an -c:v rawvideo \
  -fps_mode passthrough -f rawvideo /output.yuv
```

The launcher verifies the module size/hash before loading and uses a128MiB
resident payload profile with64MiB Wasm,1MiB packets,4MiB frames,16MiB display
queue and16384NAL units. This is a configured budget, not an isolate-memory
certification. Other API callers can supply their own bounded configuration.

The current route requires explicit passthrough frame timing, one selected AVC
video stream and rawvideo or framecrc output. Existing `-map`, codec stream selectors,
overwrite handling and frame limits are used. Bounded spatial filters, constant-size scaling and supported pixel conversion
now use the existing video filter planner. CFR scheduling, general color
metadata/range conversion, format-changing output, edit-preroll discard and
additional encode/mux paths remain to be connected. No module is downloaded or implicitly substituted.

Formal MP4 evidence covers26self-owned inputs and146mapping/frame-limit cases
through fresh Native FFmpeg, the actual Node launcher and localworkerd/R2.
Sixteen additional controls cover decode/configuration/resource faults, changing
input, cancellation, old-output preservation, successful overwrite and multipart
abort after uploaded parts. HD cases use explicit4MiB frame/64MiB Wasm budgets.
These scopes do not prove general H264/MP4 or production Workers conformity.

`avcPacketToAnnexB` validates an optional parameter prefix before copying it.
An oversized prefix is rejected before allocating its copy;384conversion
boundary cases cover owned output and supported length sizes.

Direct codec calls report declared payload-limit and Wasm allocation failures
as `H264ResourceError`, which extends `H264InputError` and exposes a `resource`
category. Categories distinguish resident, packet/frame bytes, NAL count,
pending/display queues and Wasm memory. MP4 execution maps this typed error to
`resource-budget` and retains its cause. Malformed inputs are not classified
by message text; cancellation and output cleanup/publication errors retain
their own diagnostics. Storage and other codec error taxonomies remain separate.

The formal packet corpus is documented in
`compat/behavior-specs/h264/README.md`. Its differential test compares fresh
Native output with frozen metadata/pixel hashes and the public decoder; the
Workers test runs the same vectors in localworkerd with a compiled module.


## Spatial processing candidate

Output `-vf` / `-filter:v` selects the existing bounded single-path video graph;
`-s` selects constant output dimensions and `-pix_fmt` negotiates its output
format. Existing flip, transpose, scale and format stages are reused. Their
supported syntax and pixel arithmetic limits still apply. Decoded dimensions
must stay constant. Full-range H264 and general color-metadata negotiation
are not supported by this processing path. Per-picture `metadata.colorSpace`
retains the numeric VUI matrix through delayed output. RGB conversion accepts
the default/BT601, BT709, FCC, SMPTE240M and BT2020 coefficient profiles; other matrices fail explicitly
while spatial-only YUV operations remain available.

`maxProcessingBytes` optionally reserves additional processing payload; it
defaults to `maxFrameBytes` when a transform is requested. The backend subtracts
this reservation before decoder creation, and checks filter state plus twice
the sum of intermediate frame allocations before applying the first frame.
Every intermediate frame also obeys `maxFrameBytes`. Exceeding either bound
aborts transactional output. This conservative payload accounting does not
measure total isolate memory. Untouched raw output does not reserve processing
payload. `-cpuflags 0` selects scalar pixel arithmetic; otherwise the configured
media backend arithmetic applies.

The scalar resize profile now uses scalar coefficient alignment, matching the
pinned FFmpeg source. A1918x1078-to48x32 regression previously differed by one
in four output bytes. Eighteen planar/semiplanar large reductions cover both
scalar and default profiles. H264 processing is compared in128Node CLI cases
and20workerd/R2 cases, with rollback under processing exhaustion/cancellation.
These are scoped contracts, not a general numerical conformance declaration.


### Limited-range matrix processing candidate

`metadata.colorSpace` selects the fixed reference coefficient profile for
limited-range eight-bit YUV-to-RGB output. Numeric matrices0/1/2/4/5/6/7/9
are covered; default/unspecified maps to the reference BT601 coefficients.
Tables, fractional filtered output, emulated SIMD and combined resize share
the same matrix setup. The scoped evidence is2432fresh Native pixel comparisons
and72H264workerd/R2 comparisons with Native-rewritten VUI matrices, including HD.
The already-blocked nondeterministic default aligned NV12/NV21 reference path
remains blocked; these counts exclude those cases.

Color family changes update matrix/range metadata in owned output metadata;
input metadata stays unchanged. A three-stage709YUV/RGB/601YUV/RGB regression
matches Native output. Full-range YUV-to-gray now preserves full-range luma,
including resize. Full-range YUV-to-RGB now has the scoped contracts below;
chromatic adaptation, transfer functions and complete primaries/metadata
preservation remain separate unfinished work.


The pinned Native automatic filter negotiation rejects BT2020 constant-luminance
(matrix10) to RGB. The coefficient table alone is not a supported conversion
contract: this path rejects matrix10 too. An actual CLI test checks32positive
matrix/profile/scale cases and4Native/candidate failure cases with old-output
preservation. BT2020 non-constant-luminance (matrix9) stays supported.


## Framecrc timing candidate

The MP4 route also accepts `-f framecrc` with explicit passthrough timing.
Use output `-bitexact` for comparable headers and `-enc_time_base demux`,
`filter`, or the existing bounded numeric clock syntax to select encoder time.
The default clock uses the Native MOV/rate-probe selection rather than only
STTS average rate. Frame PTS is normalized by input start time, and duration
follows the existing encoder/mux rules. Pixel checksum reads the owned tight
frame allocation directly; no whole-media or additional whole-frame copy is
needed. Rate-probe tables and header buffers reserve16896additional payload
bytes before decoder creation.

Decoder objects expose `parameters`, an immutable active-SPS snapshot with
visible dimensions, pixel format, sample aspect ratio and nominal frame rate.
It is null before the first VCL packet and after close. Reordered output keeps
its own per-picture aspect metadata; active parameters can precede those frames.
The MP4 backend applies container `pasp` before SPS aspect, and scale/transpose
update the aspect ratio. Zero-frame output still writes initialized headers.

Exact local contracts include324base Node CLI cases,15changed-clock cases,
20aspect cases and53workerd/R2 cases. Two R2 failure/cancellation cases preserve
previous output.27MP4 source tracks independently match FFprobe frame clocks.
CFR/automatic synchronization,all rate-probe termination/parameter-change cases,
TKHD-derived aspect and complete metadata handling remain unfinished/unverified.

### Full-range RGB and legacy input candidate

Eight-bit full-range matrix profiles0/1/2/4/5/6/7/9 share fixed-point
coefficient setup across conversion and resize. Legacy yuvj420p/422p/444p
inputs use ordinary planar storage while forcing full numeric range, including
when frame range metadata says limited. This follows pinned libswscale
handle_jpeg behavior. Borrowed metadata is not mutated. Same-geometry H264
range transitions retain Native decoder pixel-format behavior; direct RGB and
filter-graph outputs are compared for all four two-segment range schedules.

The isolated candidate has2432 full-range pixel comparisons,144 legacy-input
comparisons and12 spatial graph comparisons. The CLI/workerd regression batch passed, including264 NodeCLI and152 R2
comparisons plus rollback controls. Eight additional NodeCLI comparisons cover
both range-transition directions with MP4 edit lists disabled; trimming edits
remain unsupported. Canonical Linux numeric audit completed5120 comparisons with no differences
and stable reference SHA256. The locked fixture contains Native output hashes;
the portable regression runs final candidate conversion with x86_64/scalar
profiles. Reproduce with `node tools/differential-runner/fullrange-linux/generate.mjs`
using the pinned local Linux reference and container. This covers scoped numeric
paths, not default CLI Linux dispatch, full-range general conformance or
production-memory conformance.

remain unfinished. Existing nondeterministic semiplanar oracle exclusions and
Native-rejected constant-luminance matrix10 remain in force.


### Leading video edits and original file origin continuation

The isolated continuation parses leading empty video edits, true zero-entry
bodies and all-empty lists. Default MOV entry-count recovery follows actual
atom length. Each edit duration is rescaled independently before delay sums.
Active SPS parameters still require a VCL picture; no fake decoded frame is
created for an empty input. Native fails when no packet can configure its graph.

`Mp4TrackInfo.startTime` uses stream ticks and `Mp4Input.info.startTimeUs` uses
original-file microseconds before stream selection. Default copy shifts header
and payload timestamps by the same file origin, preserving later-stream delays
when an earlier stream is unselected. H264 framecrc uses that file origin too.
Positive mux DTS origins are represented with empty output edits.

The pinned generator freezes78 inputs/36 mappings; a repeat regenerated every
JSON artifact byte-for-byte. Node1296 and workerd864 H264 outputs, Node72/workerd72
remux jobs, packet/start metadata and zero-frame headers have scoped comparisons.
Node72/workerd72 all-empty controls fail while retaining candidate prior output;
Native exit183/output truncation is not claimed equivalent. Multiple media
intervals, non-unit rates, complete metadata/errors and production resources
remain unfinished. These additions are excluded from Root v28 until promoted.
